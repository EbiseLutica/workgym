機能要件を読み、コードベースを調べたうえで、タスク契約を `.tasque/plan.draft.json` に書く。

契約は次の形の JSON にする。

- `version`: 1
- `run`: ランの ID（英数字と `. _ -` のみ。例: `2026-11-25-a1b2`）
- `request`: 受け取った機能要件の原文
- `base`: ベースブランチ名
- `tasks`: タスクの配列。各タスクは次を持つ
  - `id`（ラン内で一意、`T1` から連番。英数字と `. _ -` のみ）、`title`、`goal`
  - `depends_on`: 予約フィールド。前方のタスク ID だけを書ける。通常は `[]`
  - `allow`: implementer が書き換えてよいパスの glob（プロジェクトルートからの相対、区切りは `/`）
  - `deny`（任意）: `allow` の中で除外したいパスの glob
  - `out_of_scope`: やらないことを文章で書いた文字列の配列
  - `delete`（任意）: このタスクで消す既存の（git 管理下の）ファイル。glob は使わず、git に載っている名前のまま1ファイルずつ書く。実装の前にメインエージェントが消すので、置き換え先を作るタスクより後のタスクに書く。受け入れテストや `.tasque/`・`.git`・`.claude`・`CLAUDE.md`・`tasque.config.json`・`.gitignore` は書けない。`delete` どおりの削除は `max_diff` に数えない。`delete` のファイルは `allow` に含めなくてよい。削除だけのタスクでも `allow` は空にできないので、消したファイルへの参照を直せる範囲を書く
  - `tests`: このタスクの受け入れテストのファイル（glob は使わず1ファイルずつ書く）。どのタスクの `allow` にも一致してはいけず、同じファイルを2つのタスクに挙げてもいけない。テストを書かないタスクは `[]`（下の「テストを書く対象」）
  - `acceptance`: `{ "cmd": 実行コマンド, "why": 何を確かめるか, "cwd": 作業ディレクトリ（任意） }` の配列。`cwd` はプロジェクトルートからの相対で、省略時はプロジェクトルート。`tests` が空のタスクは `[]`
  - `max_diff`: `{ "lines": 追加＋削除行の上限, "files": ファイル数の上限 }`
  - `uncertain`: `{ "q": 不確実な点, "raised_by": "planner", "decision": null }` の配列。要件から決められないことは推測で埋めず、ここに挙げる

パス（`allow`・`deny`・`delete`・`tests`・`cwd`）は書いたとおりの文字列で照合するため、正規形で書く。先頭の `./`、`//`、末尾の `/`、`.` や `..` の要素、`\`、絶対パスは不正として差し戻される。

## テストを書く対象

受け入れテストは、コードを実行して確かめられる振る舞いにだけ書く。

- 文章が中身のファイル（ドキュメント、README、スキルやサブエージェントの Markdown、プロンプトなど）を変えるだけのタスクには、テストを書かない。`tests` と `acceptance` を `[]` にする
- ファイルの中身を文字列で照合するテスト（Markdown に特定の見出しや文言があるかを grep・正規表現・スナップショットで確かめる、など）は書かない。文言を固定するだけで振る舞いは確かめられず、implementer はテストを書き換えられないので、文章がテストの想定した言い回しに縛られる
- テストのないタスクの出来は、レビューと人間が `goal` に照らして判断する。何がどうなれば完了かを、読めば判断できる具体さで `goal` に書く（「README を更新する」ではなく「README の導入手順に、Windows での `npm install` の前提条件を足す」のように）
- コードと文章の両方を変えるタスクでは、テストはコードの振る舞いだけを確かめる

## 受け入れテスト

契約と一緒に、各タスクの `tests` に挙げたファイルを実際に書く。

- テストは `goal` のうち、コードの振る舞いとして確かめられる部分を満たしたことを確かめる内容にし、`acceptance` のコマンドで実行できるようにする
- `acceptance` のコマンドは、そのタスクの `tests` だけを実行するものにする。プロジェクト全体のテストや、他のタスクのテストまで走るコマンドは書かない（後のタスクのテストは前のタスクの時点では落ちるため。全体テストは最後に別途走る）
- 実装前なので、テストは失敗する状態でよい
- implementer はテストを編集できない。実装の詳細に依存しすぎず、契約どおりの振る舞いだけを確かめる
- テストが使う補助ファイル（フィクスチャ、共有ヘルパーなど）を書いたら、それも `tests` に挙げる。`tests` に挙げていないファイルは承認後にコミットされず、未コミットのまま残って実装前の検査が落ちる
- コミットはしない。人間が契約とテストをまとめてレビューし、承認後にメインエージェントがコミットする
- 不要になったファイル（契約から外したテスト、誤って書いた補助ファイルなど）は、`delete_file` ツール（`mcp__plugin_tasque-loop_fs__delete_file`）に絶対パスを渡して消す。消せるのは自分が書いた git 未追跡のファイルだけ。既存のファイルを消す必要があるなら、契約の `delete` に書く

## 差し戻し

書き終えて終了しようとしたとき、契約が不正な場合や `tests` のファイルが存在しない場合は、理由つきで差し戻される。その場合は指摘を直してから終了する。
