# tasque-loop 仕様

機能要件や実装依頼を受け取り、タスク分割・実装・レビューを経て PR にするまでを回す Claude Code プラグイン。実行中に出た失敗や、人間の指摘で発覚した失敗をローカル台帳に記録するところまでが役割。全体の位置づけは [overview.md](overview.md) を参照。

この文書は「目指す姿」を書く。実装済みの部分の使い方は [plugins/tasque-loop/README.md](../plugins/tasque-loop/README.md) にある。どこまでできているかは末尾の「実装状況」にまとめる。

## 解決したい問題

元にした implement-loop スキルで起きていた問題と、その対策。

| 問題 | 対策 |
| --- | --- |
| 実装担当（haiku）がスコープ外まで実装する | タスク契約に許可ファイルとスコープ外を明記する。PreToolUse フックで許可リスト外の編集を拒否し、完了時に diff でも照合する |
| メインエージェントがサブエージェントを信頼せず再検証する | 検証を verify スクリプトにまとめ、その結果を証拠として受け取る。再検証はしない |
| レビュー担当（opus）が後出しで指摘を足し、ループが長引く | 1回目で全指摘を重大度つきで列挙させる。2回目は指摘が直ったかと回帰の blocker / major だけを見る。残りは繰越リストへ |
| ループが最大5回まで回る | 2ラウンドで打ち切り、人間にエスカレーションする |
| PR が巨大で読めない | 1タスク1コミット。PR 前にサイズゲートを通し、PR 本文に読む順序を書く |
| 実装量を制御できない | タスク契約に最大 diff を持たせ、超えそうなら分割し直す |
| 反省する仕組みがない | 実行ごとにローカル台帳へ記録する |

## 登場人物

- **人間**: 機能要件を渡し、契約とテストをレビューして承認する。最終の PR もレビューする
- **メインエージェント**（スキル）: 全体を進行する。ワークツリーの確認、verify の実行、テストとタスクのコミット、サブエージェントの呼び出しを担う。人間の判断を代筆しない
- **planner**（opus）: 機能要件をタスクに分割し、契約の下書きと受け入れテストを書く。ツールは Read / Glob / Grep / Write / Edit。Bash を持たず、コミットもしない
- **implementer**（haiku）: 承認済みの契約にしたがって、1タスクだけ実装する。ツールは Read / Glob / Grep / Write / Edit。Bash を持たない
- **reviewer**（opus）: 実装を観点別にレビューする。ツールは Read / Glob / Grep。2ラウンドまで

エージェントはプラグインのエージェントとして `tasque-loop:planner` のように名前空間つきで呼ばれる。プラグインのエージェントではフロントマターのフックが無視されるため、フックはすべてプラグインの `hooks/hooks.json` に置く。

## 流れ

1. 人間が機能要件を渡す
2. メインエージェントが Claude Code のワークツリーの中にいることを `check-worktree` で確かめ、`verify --phase baseline` で基点と全体テストの結果を記録する。全体テストが落ちていればランを始めない
3. planner が契約の下書き（`.tasque/plan.draft.json`）と受け入れテストを書く。SubagentStop フックが下書きを検査し、不正なら差し戻す（最大2回）
4. `verify --phase red` で、受け入れコマンドが実装前に落ちることを確かめる
5. 人間が契約・テスト・Red 確認の出力をレビューする
   - 直してほしい点があれば自由文で返す。メインエージェントはそれを planner に渡して呼び直し、3〜4 をやり直す
   - `uncertain` の判断は、人間の言葉をメインエージェントがそのまま `decision` に書く
6. 承認（`approve.mjs`）で契約を凍結する
7. メインエージェントが、契約の `tests` に挙げたパスを明示してテストをコミットする（`git add -A` は使わない）
8. タスクごとに次を回す
   1. `.tasque/current` に実行中のタスクを書く
   2. `verify --phase pre`
   3. implementer が実装する
   4. `verify --phase post`
   5. reviewer がレビューする（最大2ラウンド。超えたら人間へ）
   6. タスクを1コミットにする
9. 全タスクの後に `verify --phase pr`（サイズゲート）を通し、PR を作る。PR 本文には読む順序を書く
10. 実行結果をローカル台帳に記録する

人間待ちの間も LLM を止めない構成を目指す（キュー、ワークツリー、通知）。

## タスク契約

JSON で書く。人間がそのまま読めるよう、整形して保存する。例は [plugins/tasque-loop/examples/plan.example.json](../plugins/tasque-loop/examples/plan.example.json)。

### フィールド

- `version`: 1
- `run`: ランの ID。英数字と `. _ -` のみ（例: `2026-11-25-a1b2`）
- `request`: 受け取った機能要件の原文
- `base`: ベースブランチ名
- `tasks`: タスクの配列。各タスクは次を持つ
  - `id`: ラン内で一意。`T1` から連番。ファイル名にも使う
  - `title`、`goal`
  - `depends_on`: 予約フィールド。前方のタスク ID だけを書ける。運用してから使い道が出たときのために予約している。通常は `[]`
  - `allow`: implementer が書き換えてよいパスの glob
  - `deny`（任意）: `allow` の中で除外したいパスの glob
  - `out_of_scope`: やらないことを文章で書いた文字列の配列
  - `tests`: このタスクの受け入れテストのファイル
  - `acceptance`: `{ "cmd": 実行コマンド, "why": 何を確かめるか, "cwd"?: 実行ディレクトリ }` の配列
  - `max_diff`: `{ "lines": 追加＋削除行の上限, "files": ファイル数の上限 }`
  - `uncertain`: `{ "q": 不確実な点, "raised_by": "planner" | "implementer", "decision": 人間の判断 }` の配列。要件から決められないことは推測で埋めず、ここに挙げる

### 検証のルール

- パスはプロジェクトルートからの相対パスで、区切りは `/`。`./` で始まるもの、`..` を含むもの、絶対パスなど、正規形でない書き方は拒否する（パスの表現が複数ありうる前提で、照合の前に入口で正規形に揃えさせる）
- `tests` は自分のタスクの `allow` にも、他のタスクの `allow` にも一致してはいけない。同じテストを複数のタスクが持つこともできない
- パスの照合は、大文字小文字を区別しないファイルシステムと Unicode の正規化の違いを考え、拒否する側に倒す

### ライフサイクル

- **draft**: planner が書いた直後。構造だけを検査する
- **ready**: `uncertain` の `decision` がすべて埋まった状態
- **approved**: `approve.mjs` で `.tasque/runs/<run>/approved.json` に凍結したもの。sha256 を記録する

一度承認したタスクは変更しない（イミュータブル）。変えたくなったら、後続の新しいタスクとして足す。implementer が実行中に見つけた不確実な点は `escalate.mjs` で `escalations.json` に追記し、承認済みの契約には書き戻さない。

### 承認の条件

`approve.mjs` は次を満たさないと承認を拒否する。

- 下書きの検査が ok で、検査時・Red 確認時・現在の契約とテストのハッシュが一致する（`decision` はハッシュに含めない）
  - 一致しなければ「検査と Red 確認をやり直して」と止める
- `.tasque/baseline.json` があり、基点の全体テストが通っている
- 現在のブランチが契約の `base` ではなく、HEAD が detached でない

承認時には、基点コミット、ブランチ、テストファイルの sha256 を `approval.json` に記録する。

## 受け入れテスト

planner が契約と一緒に書く。人間は契約と一緒にテストもレビューする。

- テストは `goal` を満たしたことを確かめる内容にし、`acceptance` のコマンドで実行できるようにする
- 作ったメソッドの正常系・異常系と、引数の境界値は必ず確かめる
- implementer はテストを編集できないので、実装の詳細に依存しすぎず、契約どおりの振る舞いだけを確かめる
- 実装前なので、テストは失敗する状態でよい
- planner はコミットしない。人間の承認後にメインエージェントがコミットする（レビューのタイミングとコミットのタイミングを揃えるため）

### Red 確認の見せ方

人間がテストをレビューしやすいよう、実装前の受け入れコマンドの結果を落ち方ごとに印をつけて見せる。

- ✖ 落ちた: 期待どおり（Red）
- ⚠ 壊れている: コマンドが見つからない、起動できない、出力が多すぎる、想定外のシグナル
- ⏱ タイムアウト
- ⚠ 実装前から通った

期待どおりでないものも warning にとどめ、判断は人間に任せる。

### テストの改ざん保護

テストを承認時に作業ツリーから外して凍結する案や、タスクごとにパッチを当てる案は採らない（既存のテストファイルへの追記や共有ヘルパーを扱うと複雑になりすぎる）。代わりに次で守る。

- フックで、implementer にはラン内のどのタスクのテストも書かせない
- `post` で、どのタスクのテストも変わっていないことを確かめる
- 承認時にテストファイルの sha256 を記録し、`pr` で承認時のままかをもう一度確かめる

## 全体テスト（回帰の確認）

設定の `test_cmd` で、プロジェクト全体のテストを回す。回すのはランの最初と最後だけにする。

- **baseline**: ワークツリーに入った直後、planner がテストを書く前に1回回して結果を記録する。落ちたらランを始めない
- **pr**: 全タスクが終わった後にもう1回回し、全部通ることを要求する
- **タスクごとの post**: 合否はそのタスクの `acceptance` だけで判定する

## ガード（PreToolUse フック）

`onFailure: "block"` で fail-closed にする。契約が読めない、git に問い合わせられないなどの異常はすべて拒否に倒す。判定は `.tasque/current` があるとき（ラン中）か、tasque-loop のエージェントのときに行う。

- プロジェクトの外へのファイル操作は拒否する
- どの階層でも、`.git`・`.claude` ディレクトリと `CLAUDE.md`・`CLAUDE.local.md` には書かせない
- planner は `.tasque/` の中では `plan.draft.json` だけを書ける。`tasque.config.json` は書けない
- implementer は次に従う
  - 使えるツールは Read / Glob / Grep / Write / Edit だけ
  - 書けるのは実行中タスクの `allow` に一致し、`deny` に一致しないパスだけ
  - ラン内のどのタスクのテストも、`.tasque/**`・`tasque.config.json`・`.gitignore`・git に無視されるパスも書けない
- 書き込み先は、`~` の展開、cwd からの相対パスの解決、シンボリックリンクの解決をしてから照合する。`:`、末尾の `.` や空白、`~1` のような短縮名を含むパスは拒否する

拒否するときは、理由と「必要なら編集せずに止まって理由を報告する」旨をエージェントに返す。

## verify

検証は verify スクリプトにまとめ、その結果をメインエージェントが証拠として受け取る。結果は `.tasque/` 以下に JSON で残す。

| フェーズ | いつ | 何を確かめるか |
| --- | --- | --- |
| `baseline` | ワークツリーに入った直後、planner より前 | HEAD・ブランチ・日時と全体テストの結果を記録する。全体テストが落ちればランを始めない |
| `red` | 承認前 | 下書きの受け入れコマンドが実装前に落ちること（上記「Red 確認の見せ方」） |
| `pre` | 各タスクの実装前 | 作業ツリーがクリーン、テストがコミット済み、ベースブランチの上にいないこと。通ればタスクの基点を記録する。同じタスクに2回目は使えない |
| `post` | 各タスクの実装後 | 変更が `allow` に収まり、どのタスクのテストも変わっておらず、`max_diff` を超えず、ファイル名がどの OS でも扱え、受け入れコマンドが通ること。変更の一覧は受け入れコマンドの実行後に取り直して判定する |
| `pr` | 全タスクの後 | 基点からの変更がどれかのタスクに属し、テストが承認時のままで、ファイル名がどの OS でも扱え、PR の上限を超えず、全体テストと全タスクの受け入れコマンドが通ること |

コマンドの結果は `pass`・`fail`・`broken`・`timeout` に分類する。タイムアウト時はプロセスツリーごと止める。

## レビュー

タスクごとに、観点別の reviewer を並列で新しく起動する。ラウンドをまたいで使い回さない（前回の記憶による先入観を避けるため）。

- 観点は3つ
  - 要件: `goal` を満たすか、`out_of_scope` に踏み込んでいないか、テストを通すためだけの実装になっていないか
  - 正確性: ロジックの誤り、境界値、エラー処理、セキュリティ
  - 整合: 既存コードの流儀からの逸脱、既存ユーティリティの作り直し、不要な変更
  - スコープ・テストの合否・テストの不変・diff 量は verify が、テストの書き方は人間が見るので、reviewer の観点からは外す
- 1ラウンド目で全指摘を重大度（blocker / major / minor / nit）つきで列挙する。blocker と major を implementer に直させる。minor と nit は繰越リストに回し、PR 本文に書く
- 2ラウンド目は、1ラウンド目の指摘が直ったかと回帰の blocker / major だけを見る
- 2ラウンドで収まらなければ、人間にエスカレーションする
- メインエージェントは、誤りだと判断した指摘をコードで確かめたうえで却下できる。却下した指摘と理由は PR 本文に書く

### 並列と1体の比較

並列の3体と、3観点すべてを1体で見る方式のどちらがよいかは、まだ決めていない。2026-11-26 に同じ差分で1回だけ比べたところ、並列は 320,607 トークン・132秒、1体は 136,958 トークン・174秒だった。major は両方が見つけたものが2件、並列だけが1件（README の記述が古い）、1体だけが2件（どちらも実装を深く読む正確性の問題）で、minor は並列のほうが多かった。1回分では決められないので、当面は両方を走らせてデータを貯める。

- 1ラウンド目だけ、観点別の3体と同じメッセージで1体も並列に起動する。2ラウンド目は修正の確認と回帰だけなので、方式の差が出にくく、並列の3体だけにする
- 指摘をまとめるときは並列と1体の指摘を突き合わせ、指摘ごとに出どころを `found_by`（`並列:要件`・`並列:正確性`・`並列:整合`・`1体`）として残す。1体だけの指摘も `perspective` は3観点のどれかに振る
- 1体の指摘も、並列の指摘と同じ基準で直す・却下する・繰り越すを決める
- 台帳には、1ラウンド目の指摘を、両方・並列だけ・1体だけに分けた数と、それぞれで却下された数を残す。却下の数は誤検出の率を見るため

### 修正とエスカレーション

- post の失敗もレビューの指摘も、implementer を呼び直して直させる（ガードの許可リストが効いたまま直させるため）。post の失敗を直させるのは2回まで
- implementer が契約では決められない点を見つけたら、編集をやめて報告する。メインエージェントは `escalate.mjs` で記録し、そのタスクで止めて人間に聞く。回答はそのまま implementer に渡す。契約そのものを変える必要がある回答なら、そのランでは進めない
  - implementer の文章はシェルに通さず、ファイルに書いて `--q-file` / `--context-file` で渡す
- 修正中に implementer が異議を返した場合、reviewer の指摘への異議はメインエージェントが判断して却下できる。verify の結果（テストや検査）への異議は却下できず、エスカレーションに回す
- 止まった後に再開するときは、post の修正回数とレビューのラウンド数を引き継ぎ、止まった段階から続ける

### 人間のレビュー結果の扱い

- 契約とテストへの人間の指摘は、自由文のまま planner に渡して呼び直す
- 各回のレビューは `.tasque/plan.draft.reviews.json` に記録し、承認時にランのディレクトリへ移す。人間の意思決定の記録として、後で台帳に使う

## ワークツリー

tasque-loop はワークツリーを作らない。Claude Code がセッションを開くときに作ったワークツリーの中で作業する。始める前に `check-worktree` で、その中にいることを確かめる。

- Claude Code はワークツリーに入っても `CLAUDE_PROJECT_DIR` を元のリポジトリのまま渡す。そのためフックと CLI は、作業場所（cwd）側のワークツリーをプロジェクトとして扱う
- cwd のリポジトリが `CLAUDE_PROJECT_DIR` と同じリポジトリ（git の共通ディレクトリが同じ）のときだけ、ワークツリー側を採る。別のリポジトリなら `CLAUDE_PROJECT_DIR` を使う
- プロジェクトがリポジトリのサブディレクトリ（モノレポ）なら、同じオフセットをワークツリー側にも当てる
- git は 2.31 以上が必要
- ワークツリーの中で Bash の cwd はワークツリーのルートになり、`CLAUDE_PROJECT_DIR` も渡らない。そのためスキルは、`git rev-parse --show-toplevel` と `git rev-parse --show-prefix` をつなげて `<P>` を求め（位置が空でルートに `tasque.config.json` がなければ人間に確かめて止まる）、コマンドのたびにそこへ cd する

### ワークツリーの寿命

`.tasque/` は git に無視されているので、ワークツリーを消すとランの記録（契約、verify の結果、エスカレーション）も消える。承認後のランの記録は、区切りごとに台帳へ写しておく（後述）。ワークツリーの削除はハーネス（Claude Code のセッションのアーカイブなど）に任せ、tasque-loop からは消さない。

- **開始**: `check-worktree` で、リンクされたワークツリーの中にいて、`.tasque/current` がなく、未コミットの変更がないことを確かめてから始める。満たさなければ止まり、ワークツリーありで開き直すよう伝える。途中からの再開は今は扱わない（止まったセッションで続ける）
- **途中で止まったとき**: ワークツリーからは出ず、`.tasque/current` も残す。ワークツリーの場所と止まった段階を報告する
- **PR 作成後**: セッションはワークツリーに残ったまま終わる。PR に修正が入りうるので消さない

## 設定（tasque.config.json）

プロジェクトルートに置く。すべて任意。

| キー | 既定値 | 説明 |
| --- | --- | --- |
| `test_cmd` | `null` | プロジェクト全体のテスト。文字列か `{ "cmd": "...", "cwd": "..." }` |
| `diff_exclude` | `[]` | diff 量の計算から外すパスの glob（lockfile、生成物など）。スコープの照合からは外さない |
| `command_timeout_sec` | `600` | コマンド1本あたりのタイムアウト |
| `pr` | `{ "max_lines": 500, "max_files": 10 }` | PR のサイズ上限 |

設定ファイル自体は git で管理する前提で、ハッシュでの保護はしない。git に無視されていると新しいワークツリーに入らないので、warning を出す。誤って変更をコミットしても `pr` のスコープ検査でどのタスクにも属さない変更として引っかかり、戻すのも簡単なので、それ以上は守らない。

将来、保護パスの追加やレビュー観点の追加もこの設定に置くことを想定している。

## 安全

- `red`・`post`・`pr` は planner や implementer が書いた、レビュー前のコードを実行する
- これは Claude Code のサンドボックスとワークツリーでまとめて守る方針にする。ただしサンドボックスはネイティブ Windows では使えないので、必須にはせず、README で推奨するだけにする。スキルはサンドボックスの面倒を見ない

## ローカル台帳への記録

記録は決まった項目をスクリプトが機械的に書く。LLM の自由記述に任せない。材料はランの実行中に各スクリプトが残す。

| 材料 | 書くもの | 置き場所（`.tasque/runs/<run>/`） |
| --- | --- | --- |
| 人間のレビュー（verdict と原文、その時点の下書きのハッシュ） | `review-feedback.mjs` | `reviews.json`（承認時に下書き側から移す） |
| エスカレーションと人間の回答 | `escalate.mjs`・`answer.mjs` | `escalations.json` |
| post の試行（合否、落ちた check、スコープ外のパス） | `verify --phase post` | `tasks/<id>.post-history.json` |
| reviewer の指摘（観点、重大度、扱い、却下の理由、出どころ） | `record-review.mjs` | `tasks/<id>.review-<1か2>.json` |
| PR のサイズ | `verify --phase pr` | `tasks/pr.json` |

台帳には1ランを1ディレクトリで置く（`<プロジェクト名>/<run>/`）。`ledger.mjs --run <run>` は呼ぶたびに次の2つを書き直し、変化があればそのランのパスだけをコミットする。

- `raw/`: `.tasque/runs/<run>/` を丸ごと写したもの。上の表の材料がすべて入る。コピー元で消えたファイルは `raw/` からも消す
- `record.json`: 上の材料を集計した要約（`buildRecord` の出力）。`raw/` から作り直せるもので、`raw/` にない情報は足さない。記録した時刻は入れない（台帳のコミット時刻で分かる）

run スキルは、承認してテストをコミットした後・各タスクをコミットした後・PR を作った後・PR に修正を足した後・承認後に途中で止まる前に呼ぶ（承認前は呼ばない）。台帳の HEAD と比べて `<プロジェクト名>/<run>` に変化がなければ、「変化なし」を出してコミットせずに終わる。`record.json` が前にコミット済みでも失敗しない。

- `record.json` の項目: プロジェクト、ラン、タスクごとの post の試行回数と失敗した check、スコープ違反のパス、レビューのラウンド数と重大度・扱い別の指摘数、2ラウンド目の指摘数（後出しの数）、1ラウンド目の指摘の出どころ別の数（両方・並列だけ・1体だけと、それぞれの却下の数）、PR のサイズ、人間の判断（レビューの原文、`uncertain` の決定、エスカレーションの質問と回答）
- プロジェクト名は元のリポジトリのディレクトリ名（ワークツリーでも git の共通ディレクトリから求める）。モノレポではサブディレクトリまで含める
- 台帳はマシンごとの独立した git リポジトリ（remote なし、プロジェクトツリーの外）。場所は `TASQUE_LEDGER_DIR`、なければ `~/.tasque/ledger`。なければ作る。中身のある git 管理外のディレクトリは使わない
- 承認済みのランでなければ exit 1 にする。台帳の場所が使えないとき、台帳へのコミットに失敗したときも exit 1 にする
- 変化の判定は台帳の git の HEAD を基準にする（`raw/` と `record.json` を書いたあとに `git add -A -- <プロジェクト名>/<run>` してから、差分が空かを見る）。前回のコミットに失敗して残ったファイルも、この判定で拾える
- コミットに失敗したら、書いたファイルは戻さずにやり直しを促す。もう一度呼べば、その時点の `raw/` と `record.json`（残っていたものを含む）でコミットされる
- 同じ run ID による上書きは許容する（上書きを防ぐ仕組みは入れない）
- 「その他、実行中に気づいた反省点」のような自由記述は、今は記録しない
