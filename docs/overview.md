# 自省サブシステム 全体構想

このリポジトリで管理する3つのサブシステム（tasque-loop / ledger-sync / kaizen-kaigi）の目的と関係をまとめる。各サブシステムの詳細はそれぞれの仕様書に書く。

- [tasque-loop](tasque-loop.md)
- ledger-sync（未着手）
- kaizen-kaigi（未着手）

## 背景と目的

LLM の実装速度に対して、人間のレビュー速度が律速になっている。

- LLM が書く設計書・コード・テストが膨大で、読みきれない
- 人間が読んでいる間、LLM は止まっている
- 結果として、人間レビューの遅さが LLM の速さの足を引っ張っている

これを、レビューの負荷を下げつつ最終レビューは人間が持つ形で解消する。そのうえで、仕組みを全プロジェクト・全マシンで使い回し、失敗例をもとに改良し続ける。

- 意思決定と実装の多くを LLM に移譲し、人間の認知負荷を下げる
- 最終レビューは人間が行う
- この仕組みを関わる全プロジェクトで共通化する
- 失敗の反省（自省）も全プロジェクト横断で共有し、ループ自体を改良する
- 分散した各マシンの Claude Code（個人の開発マシン、仕事のマシン、ローカルネットワーク内の常時起動の台帳サーバー。例えば Raspberry Pi）で動かす

「マルチエージェントで認知負荷が下がる」という話の実体は、人間側のセッション管理を肩代わりする層（オーケストレーション層）が効いている、というものだった。エージェント体制そのものより、人間が見る対象を減らす設計のほうが本質だと考える。

## 設計原則

- 人間のレビューを前倒しする（計画・タスク契約の段階で見る）
- 成果物の全部ではなく、判断と不確実な点を見る
- 機械検証を先に通し、その後に人間が見る
- 人間待ちで LLM を止めない（キュー、worktree、通知）
- 外に出るものは必ずレビューゲートを通す（失敗時は閉じる）
- 守りはプロンプトの文面ではなく、スクリプトや OS で機械的に強制する
- 秘匿情報を消す方式より、書いてよい項目だけを通すスキーマ（ホワイトリスト）方式にする
- 承認の経路は人間専用にする
- マシンの外に出すのは汎用的な情報だけにする。ドメイン知識や個人情報に由来する情報は外に出さない（次節）

## 情報の扱い

このリポジトリ（仕組み）は GitHub で公開し、tasque-loop も公開のリポジトリ上で更新していく。そのため、台帳から生まれた改良は最終的に公開されうる。これを前提に、情報を置き場所ごとに分ける。

| 置き場所 | 持ってよい情報 | 外に出るか |
| --- | --- | --- |
| ローカル台帳（各マシン） | あらゆる情報。タスクの題名、人間のレビューの原文、決定、エスカレーションなど、ドメイン知識や個人情報を含みうる生の記録 | 出ない |
| ledger-sync（各マシン） | ローカル台帳のすべてと除外リストを読める | 外へ出すのは、スキーマを通った汎用的な一般則だけ |
| リモート台帳・kaizen-kaigi | 承認済みの一般則だけ | kaizen-kaigi の改良を通じて公開されうる |
| このリポジトリ | 仕組みのコードと文書だけ | 公開 |

- **外向きのサニタイズは ledger-sync の役目**にする。ledger-sync だけがローカル台帳の生の情報と外の世界の両方に触れる。tasque-loop はローカル台帳に生のまま書き、外に出すことを考えない
- ledger-sync での人間の承認は、「**公開されてもよいか**」の判断として扱う。リモート台帳に入った一般則は、kaizen-kaigi の改良を通じて公開されうるため。承認 UI の文言もそう書く
- 汎用かどうかは機械では判定しきれないので、機械で狭められるところは狭める。一般則のスキーマは選択肢・数値・決まったカテゴリを中心にし、自由記述は1項目に限って長さの上限を設ける。除外リストとの照合は自動で通す。最後に人間が項目ごとに承認する
- kaizen-kaigi は、PR の本文・コード・テストに台帳の文面を引用しない。根拠は一般則の ID で示す
- ledger-sync を入れないマシンも認める。そのマシンでは tasque-loop だけが動き、ローカル台帳はそのマシンに留まる（台帳の記録は自省の材料にならないが、仕組みは同じように使える）

## 全体像

各マシンの tasque-loop が失敗をローカル台帳に残し、ledger-sync を入れたマシンからは、承認を通った一般則だけが 台帳サーバーに届く。kaizen-kaigi がそれを読んで改良を提案し、人間がマージした tasque-loop が GitHub から各マシンに戻る。

```
[ledger-sync を入れたマシン]                 [台帳サーバー]
tasque-loop ──記録──> ローカル台帳
                         │
                   ledger-sync（一般則へ変換・サニタイズ）
                         │
                      pending ──人間が承認──> リモート台帳
                      （公開されてよいか）          │
                                             kaizen-kaigi（改良案を PR に）
                                                  │
                                         人間がマージ = リリース
                                                  │
tasque-loop <──── GitHub（公開リポジトリ・マーケットプレイス）

[ledger-sync を入れないマシン（仕事のマシンなど）]
tasque-loop ──記録──> ローカル台帳（このマシンから出ない）
tasque-loop <──── GitHub から入れるだけ
```

## tasque-loop

機能要件や実装依頼を受け取り、タスク分割・実装・レビューを経て PR にするまでのベストプラクティスを、Claude Code のプラグインにしたもの。実行中に出た失敗や、人間の指摘で発覚した失敗をローカル台帳に記録するところまでが役割。詳細は [tasque-loop.md](tasque-loop.md)。

## ledger-sync

その日に溜まったローカル台帳を処理し、汎用的な一般則だけをリモート台帳へ commit し、push する。ローカル台帳のあらゆる情報を読めるが、外へ出すのはスキーマを通り、人間の承認を通ったものだけ。外向きのサニタイズを一手に引き受ける（「情報の扱い」を参照）。

### 台帳の3段構成

| 段 | 場所 | 中身 |
| --- | --- | --- |
| ローカル台帳 | マシンごとの独立 git リポジトリ（remote なし、プロジェクトツリーの外） | tasque-loop が記録した生の記録。復旧しやすいよう commit して残す。このマシンから出ない |
| pending | ローカル台帳とリモート台帳のどちらのリポジトリの外にも置くステージング | 原本から作った、共有候補の「一般則」。承認待ち |
| リモート台帳（集約） | 台帳サーバー上の別 git リポジトリ | 承認済みの「Claude Code を使ううえでの一般則」だけ。原本は不透明な ID で参照する |

不要になった履歴は、後から `git filter-repo` で消せる。対象はローカルネットワーク内の台帳サーバーだけなので、万が一あげてしまっても消して直せる。

### 承認ゲート（毎日19時ごろ）

1. ローカル台帳の反省をまとめ、pending に一般則として積む
2. 通知を出す（terminal-notifier を想定）
3. 人間がブラウザでローカルの Web サーバーを開く。JSON と静的 UI（Vue.js）で作り、AI が生成した HTML は使わない
4. 項目ごとのチェックボックス（初期は未チェック）を選び、submit する
5. 承認サーバー自身が commit と push を行う。タイムアウトでの自動送信はしない
6. 未承認の項目は pending に残すか、明示的に破棄する

表示する内容は、変換後の「一般則」のフィールドだけに限る。出力はエスケープし、`v-html` は使わない。顧客情報の除去は伏せ字にする方式ではなく、書いてよいフィールドを決めたスキーマ（ホワイトリスト）にしたがう。

### 自動・手動モード

- 自動（既定の候補）: 上記の19時の流れをそのまま回す
- 手動: 記録と pending への集約は裏で動くが、push 前に明示の許可を求める
- モードはマシンごとのローカル設定に置き、push スクリプトの内部で強制する（プラグイン側には置かない）
- 仕事のマシンには当面 ledger-sync を入れない（「配布と運用」を参照）

### 除外リスト

- 当面、個人情報とドメイン知識は一般則の対象外にする
- 除外したものを「除外リスト」として覚えておき、ledger-sync が次回以降の候補判断に使う
- 除外リストには顧客名や固有名詞など、それ自体が機微な内容が入りうる。リストはローカル台帳と同じ場所に置き、リモート台帳には送らない
- ledger-sync の判断に Claude Code を使う場合、リストはそのセッションの入力に入る。出力（pending）にリストの中身が混ざらないかを承認 UI で確認する
- リスト自体の整理（古い項目の削除、重複のまとめ）が必要。承認 UI で項目を外すときに「除外リストへ追加」を選べるようにする
- 一致判定は機械的に（文字列照合で）行う。ドメイン知識は列挙しきれないので、書いてよいフィールドを決めたスキーマを主、除外リストを補助にする

## kaizen-kaigi

リモート台帳を持つ台帳サーバーでだけ動く。その日に更新されたリモート台帳を定時処理で読み、今の tasque-loop に対する改良策を考えて PR にする。人間がマージした改良は GitHub の公開リポジトリから各マシンに届き、ループが閉じる。

### 役割

- 入力: ledger-sync で承認されたリモート台帳（一般則のみ）
- 処理: 定時に読み、tasque-loop への改良策を考える
- 出力: tasque-loop のスキル・フック・スクリプトの変更案。最終的に公開されるので、台帳の文面は引用せず、根拠は一般則の ID で示す
- 配布: GitHub の公開リポジトリをプラグインマーケットプレイスにする

### 改良の対象（案）

失敗の種類で、直す場所を分ける。機械で止められるものほど、文章のルールにしない。

| 失敗の型 | 直す場所 |
| --- | --- |
| 機械的に検出できる（スコープ逸脱、サイズ超過） | フックと verify スクリプト |
| レビューの後出し指摘のパターン | レビュー観点（ルーブリック） |
| プロジェクト固有の癖 | そのプロジェクトの CLAUDE.md とプロジェクト設定 |
| 自分の判断の癖 | `~/.claude/CLAUDE.md` |

効果が見えないルールは定期的に削る。失敗は再現できる形（タスク契約、diff 統計、レビュー指摘）で残し、機械的な失敗は決定的に再現テストできるようにしておく。

### 改良の反映方針（決定）

自動でスキルを書き換えて配布すると、改悪が全マシンに広がる。候補は次の3つだった。

- A. 提案のみ: 改良策をブランチや PR として積み、人間がマージしたときだけ配布する
- B. 自動適用: 改良策をそのままマーケットプレイスに反映する
- C. 検証付き自動適用: 過去の失敗ケースを再現して改善を確かめ、通ったものだけ反映する

**A から始める。** 再現ケースが貯まったら C へ移ることを検討する。B は、最終レビューを人間が持つという目的の根幹を人間の目の外で書き換えることになるので採らない。

### 実行方式

- 起動: 台帳サーバーの cron が毎日 `tmux new-session -d` で `claude --remote-control "<提案作成の指示>"` を起動する。対話セッションなので、claude.ai/code やスマホから進行とログを見られる。毎回新しいセッションなので、文脈は日をまたいで混ざらない
- 提案の出し方: 改良案はブランチと PR で出す。kaizen-kaigi のトークンはブランチと PR の作成だけができ、マージはできない。人間がマージするとマーケットプレイスの main が更新され、各マシンに届く（マージがリリース）。PR の出し先（GitHub に直接出すか、台帳サーバー上の Forgejo で一度受けてから人間が GitHub に出すか）は未決
- 直させ方: その PR の tmux セッションに Remote Control でつないで直接指示する。小さな直しは Forgejo の Web エディタで行う。修正は2〜3回までを目安にする
- 維持と閉じ方: セッションは PR がマージかクローズされるまで維持する。tmux のセッション名は PR ごとに一意にする。見張りの cron が Forgejo の API で PR の状態を定期的に引き、マージ・クローズ済みのものと、作成から3日たったもの（PR もクローズする）のセッションを落とす。台帳サーバーの再起動などでセッションが落ちたときだけ `claude --resume` で復旧する
- 注意: 初回のフォルダ信頼ダイアログが無人起動を止めるので、対象フォルダは事前に信頼済みにする。権限確認は許可ルールとサンドボックスで先に絞っておき、出たものはスマホから許可する。Remote Control にはフルスコープのログイン（`setup-token` は不可）が必要

## 安全設計

守りはプロンプトの文面ではなく、OS やスクリプトで機械的に強制する。理想は、台帳の push を人間の承認サーバーだけにしかできないようにすること。

### 脅威

- tasque-loop や台帳記録のセッションが、承認を経ずに台帳を push してしまう
- エージェントが承認用 UI を自分で走らせて、自分で承認する
- 鍵や台帳をエージェントが読めてしまう
- 台帳に顧客情報や社内の秘密が混ざる

仕事のマシンには、当面 ledger-sync を入れない。そこで生まれたローカル台帳はマシンの外に出ないので、仕事のドメイン知識や顧客情報が台帳の経路で外に出ることはない。仕事のマシンでは、所属先の方針の範囲で、自分で信頼性を確かめた公開リポジトリの tasque-loop を入れて使うだけにする。

### 対策

| 対策 | 内容 |
| --- | --- |
| Claude Code のサンドボックス | 有効にし、`allowUnsandboxedCommands: false`、`failIfUnavailable: true` にする。macOS は Seatbelt、Linux・WSL2 は bubblewrap。ネイティブ Windows は未対応 |
| 読み取り範囲の制限 | サンドボックスは既定でマシン全体を読めるので、`denyRead` / `allowRead` で鍵・台帳・承認 UI のパスを絞る |
| 組み込み Read / Edit / Write の扱い | サンドボックスは Bash のみが対象。組み込みツール・フック・ローカル MCP は外にあるので、permission の deny ルールで同じパスを塞ぐ |
| push の担当 | Claude Code のセッション（台帳記録用を含む）は台帳の commit も push もしない。台帳用セッションが書けるのは pending ファイルだけ。承認サーバーが commit と push を行う |
| 承認サーバーの置き場所 | 承認サーバーと UI のコード、push 用の鍵は、エージェントが読み書きできないパスに置く。Claude Code からは起動しない。鍵は git-shell 専用ユーザーの専用鍵にする |
| 承認の入口 | 人間専用。エージェントが API を直接叩いて承認できてしまう点は許容する（送り先はローカルネットワーク内の台帳サーバーだけで、リモート台帳の履歴は後から消せる）。ただし、リモート台帳から kaizen-kaigi を経て公開された改良は消せないので、kaizen-kaigi の PR は人間がマージ前に読む |
| フック | 二次的な守り。fail-closed（`onFailure: block`）の許可リスト方式にする。「台帳用セッション以外は git 操作を止める」をフックだけに任せることはしない |
| 顧客情報の除去 | 伏せ字ではなく、書いてよいフィールドを決めたスキーマで通す。さらに人間が項目ごとに承認する |

### 注意点

- サンドボックスの中からは SSH が proxy を無視するので push できない。通常の PR フローでは HTTPS リモートを使うか、`excludedCommands` を使う
- 台帳のすり抜けは完全には防げない。ただしリモート台帳はローカルネットワーク内の台帳サーバーの git だけで、後から履歴ごと消せるので、被害は限定的と見ている。公開リポジトリに入ったものは消せないので、公開の手前（kaizen-kaigi の PR のマージ）でも人間が見る

## 配布と運用

tasque-loop は GitHub の公開リポジトリから配布し、各マシンでプラグインとして入れる。Windows と Linux でのテストは GitHub Actions で回す。

### マシンごとの役割

| マシン | 動かすもの | モード |
| --- | --- | --- |
| 個人の開発マシン（複数） | tasque-loop、ledger-sync（ローカル台帳と承認ゲート） | 自動（候補） |
| 仕事のマシン | tasque-loop だけ（GitHub から入れる）。ledger-sync は入れず、ローカル台帳はこのマシンから出ない | — |
| 台帳サーバー | kaizen-kaigi、リモート台帳 | — |

### 配布の仕組み

- このリポジトリをプラグインマーケットプレイスにする（`.claude-plugin/marketplace.json`）。`claude plugin marketplace add` と `claude plugin install` で入れる
- プラグインにはスキル、サブエージェント定義、フック、MCP を束ねられる。公開前に `claude plugin validate` で検査する
- モード設定と鍵はプラグインに入れず、マシンごとのローカル設定に置く
- 自動更新: マーケットプレイスの登録で `autoUpdate: true` を指定すると、バックグラウンドで更新される（[公式ドキュメント](https://code.claude.com/docs/en/plugins/org)）。自前のマーケットプレイスは既定でオフ。同ドキュメントの例は managed settings で、ユーザー設定でも同じキーが効くかは未確認
- 効かなければ、`claude plugin marketplace update` と `claude plugin update` を定時に呼ぶ仕組みを足す。更新を実行中のセッションに反映するには `/reload-plugins` か新しいセッションが必要

### 仕事のマシンでの運用

- tasque-loop を GitHub から入れるだけにする。ledger-sync は入れない
- tasque-loop はローカル台帳に記録を書くが、そのマシンの外には出さない。台帳の場所は `TASQUE_LEDGER_DIR` で変えられる
- 将来 ledger-sync を入れるかは、一般則のスキーマとサニタイズの仕組みができてから改めて決める

## 未決事項

### 実環境での検証が要るもの

- 無人の tmux 起動が止まらないか（フォルダ信頼ダイアログ、権限確認）
- マーケットプレイスの更新が各マシンにどう反映されるか（自動更新の挙動）
- Remote Control の接続が切れたときにセッションがどう終わるかと、再起動後に `claude --resume` で復旧できるか
- 失敗を再現できる形で残す形式（タスク契約、diff 統計、レビュー指摘の持ち方）
- 見張りの cron が PR の状態を引き、対応する tmux セッションを落とす仕組み

### 詳細設計で決めるもの

- 一般則のスキーマ（リモート台帳に書いてよいフィールドをどこまでにするか）。リモート台帳の一般則は公開されうる前提で決める
- kaizen-kaigi の PR の出し先（GitHub に直接か、台帳サーバー上の Forgejo で受けてから人間が GitHub に出すか）
